# Процесс разработки

Владелец: MEMBER_A. Правила рассчитаны на хакатон: просто, быстро, без лишней инфраструктуры.

## 1. Принципы

- Маленькие изменения: одна задача — одна ветка — один PR.
- Интегрируемся часто: PR в main хотя бы раз в 2 часа, не копим работу до вечера.
- main всегда собирается и проходит `make check`.
- Владелец файла решает, что в нём меняется (`python3 tools/tasks.py owner PATH`).
- Доказательства вместо слов: в PR — команды проверки и их результат.

## 2. Ветки

- Имя: `<буква участника>/<ID задачи>-<кратко>` — `a/INFRA-02-contracts`, `b/EARTH-02-terrain`, `e/SCI-03-pairs`.
- Ветка живёт часы, а не дни. Перед PR: `git fetch && git rebase origin/main` (или merge main).
- Прямой push в main и force push в общие ветки запрещены (защита main — PREP-03).

## 3. Коммиты

- Сообщение на английском, в повелительном наклонении, с ID: `ENG-02: add exact shortlist search and greedy check`.
- Если помогал ИИ — трейлер `Co-Authored-By: Claude <noreply@anthropic.com>` (или имя используемой модели). Это часть раскрытия ИИ по правилам NASA.
- Без имён людей в сообщениях — только MEMBER_X или ники.

## 4. Pull request и ревью

- Шаблон `.github/pull_request_template.md`: задача, что сделано, как проверено (команды → результат), чек-лист.
- Размер — до ~400 строк изменений, иначе разбить.
- Ревьюер: MEMBER_A; для `pipeline/engine/` и `pipeline/common/terrain.py` — MEMBER_D; если затронут чужой модуль — его владелец. Научные утверждения — MEMBER_E.
- Время ответа на ревью во время хакатона — до 15 минут; ревью проверяет контракт, науку, тесты, отсутствие секретов и больших файлов, владение файлами.
- Слияние: «Squash and merge», заголовок PR = `ID: …`.

## 5. Проверки

| Проверка | Команда | Когда |
| --- | --- | --- |
| Реестр задач и документы | `python3 tools/tasks.py validate` | всегда, уже сейчас |
| Линтер Python | `ruff check pipeline` | после INFRA-01 |
| Тесты Python | `pytest -q` | после INFRA-01 |
| Контракты | `python -m pipeline.contracts.validate <файлы>` | после INFRA-02 |
| Типы TypeScript | `npm --prefix web run typecheck` | после INFRA-01 |
| Тесты сайта | `npm --prefix web test -- --run` | после INFRA-01 |
| Сборка сайта | `npm --prefix web run build` | после INFRA-01 |
| Всё сразу | `make check` | перед каждым PR |
| Сквозной сценарий | чек-лист IC-3 в INTEGRATION_STATUS.md | на точках интеграции |
| Научные тесты | E1 (LIGHT-01), E2 (TERR-01, EARTH-05), E3 (VAL-01), E4 (ENG-02), E7 (VAL-02), E10 (ENG-03) — VALIDATION_PROTOCOL | по плану |

Модульные тесты лежат рядом с кодом: `pipeline/<модуль>/tests/test_*.py`, `web/src/**/*.test.ts`.

## 6. CI

GitHub Actions (INFRA-04) на каждый PR и push в main: `tools/tasks.py validate`, ruff, pytest, typecheck, vitest, build и поиск шаблонов секретов (`AIza`, `-----BEGIN`, `ghp_`, `"private_key"`). Падение блокирует merge. До INFRA-04 те же проверки запускаются локально через `make check`.

## 7. Протокол изменения контракта

Контракты v1 замораживаются в Сб 11:00 (INFRA-02).

1. Автор пишет предложение в #general: что меняется, зачем, кого касается.
2. Потребители (по INTEGRATION_STATUS §1) отвечают «ок» или возражают — 10 минут.
3. MEMBER_A меняет схему, пример и `web/src/types/contracts.ts`, повышает версию: patch — описание; minor — новое необязательное поле; major — переименование, удаление или смена смысла (после заморозки — только в крайнем случае).
4. Производители и потребители обновляют код в своих ветках.
5. Запись в INTEGRATION_STATUS §3.

## 8. Конфликты

- Конфликт в своём файле — решаете сами, перезапускаете проверки.
- Конфликт в чужом файле — не решаете, зовёте владельца.
- `project/tasks.json` — обычно сливается сам (разные задачи — разные строки). Если конфликт — оставить обе правки статусов, затем `python3 tools/tasks.py validate`.
- Сгенерированные разделы документов — принять любую сторону и запустить `python3 tools/tasks.py render`.
- `docs/planning/PROGRESS.md` — каждый пишет в свой раздел, конфликтов почти нет.

## 9. Секреты и большие файлы

- Не коммитим: `.env`, ключи, токены, JSON сервисных аккаунтов, учётные данные GEE (`.gitignore` уже защищает основные шаблоны).
- Не коммитим: GeoTIFF, NetCDF, HDF, архивы, видео. Они живут в `data/raw/` и на дисках.
- В git — маленькие обработанные JSON (`data/processed/`, ≤ 5 МБ на файл) и WebP-кадры «То же Солнце» (P1, ≤ 150 КБ на кадр).
- Ключ попал в коммит — сразу сообщить MEMBER_A, перевыпустить ключ, переписать историю.

## 10. ИИ в коде

- Первая строка файла, написанного с заметной помощью ИИ: `# Written with AI assistance (Claude Code); reviewed by MEMBER_X.` (`//` для TS).
- Трейлер коммита (§3) и строка в `docs/ai-log.md` для заметных кусков работы.
- Код от ИИ проверяет человек: запускает тесты и читает diff.
- В ИИ-инструменты не вставляем ключи и персональные данные.

# Протокол проверки

Владельцы: MEMBER_D (движок, E3–E7, E10), MEMBER_C (освещение и рельеф целей, E1, E8, E9), MEMBER_B (сверка Земли, E2b), MEMBER_E (научная оценка, правила исключения). Протокол замораживается коммитом пререгистрации на KICK-01 до обработки любых данных. **Ожидаемые «успешные» результаты не записываем** — только вопросы, гипотезы, процедуры и критерии.

## 0. Общие правила

1. **Пререгистрация:** вопросы, гипотезы, метрики, критерии, правила исключения и параметры (§12 MATHEMATICAL_SPECIFICATION) коммитятся до первого запуска (DEC-010). `practice_sites.csv` коммитится до первого запуска VAL-01. Хэш коммита пишется в `validation.json`.
2. **Без подгонки:** параметры и пары не меняются после первого запуска E3. Если меняются — публикуем оба результата с пометкой, что второй получен после просмотра первого.
3. **Четыре исхода.** `confirmed` — критерий выполнен; `not_confirmed` — критерий не выполнен; `inconclusive` — данных меньше порога (например, проверяемых пар меньше 8) или доверительный интервал накрывает и успех, и провал; `not_run` — не успели или не применимо. Все четыре показываются одинаково заметно.
4. **Отрицательные результаты** публикуются на экране Evidence и в README наравне с положительными. Формулировка: «гипотеза не подтвердилась; возможные причины: …; что это значит для пользователя: …». Утверждение, опирающееся на неподтверждённый эксперимент, снимается из подачи (SCIENTIFIC_CLAIMS_REGISTER).
5. **Воспроизводимость:** фиксированный seed 2026, версии наборов в `provenance`, sha256 входов в результатах, команда `make data`.
6. **Сводка:** все эксперименты пишут результат в `data/processed/validation.json` (схема — API_AND_SCHEMA_CONTRACTS §2.6).

## 1. Какие проверки выбраны и почему

| Тип проверки (из задания) | Решение | Почему |
| --- | --- | --- |
| Сравнение с известными аналоговыми площадками | **E3 (P0)** | Главная внешняя проверка: места, которые NASA использовала для конкретных задач |
| Сравнение с простыми базовыми линиями | **E3 (P0)**: «только сухость», случайная, v1-сходство | Без базовой линии высокий ранг ничего не доказывает |
| Устойчивость к весам | **E5 (P1)** | Веса заданы экспертом — нужно знать, насколько от них зависит ответ |
| Устойчивость к масштабу | **E9 (P1)**, объяснительный | Показывает, почему нужны одинаковые базы для трёх тел |
| Чувствительность к пропускам | **E5 (P1)**: маскирование 10 % атрибутов | Пропуски реальны (LST над льдом, края покрытия) |
| Повторяемость запусков | **E10 (P0)** | Дешёво и обязательно для воспроизводимости |
| Альтернативные научные представления | **E6 (P1)**: абляция групп атрибутов, «жёсткое И» вместо геометрического среднего | Проверяет, что решает каждая часть модели |
| Корректность вычислений | **E1, E2, E4 (P0)**, E8 (P1) | Без этого остальные проверки бессмысленны |
| Отрицательные контроли | **E7 (P0)** | Заведомо неподходящие квадраты не должны выигрывать |
| Открытие ранее не замеченных площадок | **Не проверяется как эксперимент** | За два дня нельзя подтвердить «открытие» без поля; новые площадки называем кандидатами, геолог смотрит их в SCI-05 |
| Пригодность площадки для миссии | **Вне объёма** | Сходство условий ≠ пригодность (доступ, разрешения, логистика); на сайте — «Suitability not assessed» |

## E1. Точность положения Солнца (P0; LIGHT-01, сводка — VAL-01)

| | |
| --- | --- |
| Вопрос | Совпадает ли наша реализация алгоритма NOAA с независимым эталоном? |
| Гипотеза | Максимальное отклонение геометрической высоты Солнца от astropy ≤ 0,1° при h > 1° |
| Переменные | Независимые: широта (−80°, −77,5°, −45°, 0°, 45°, 70°, 80°), дата (два равноденствия, два солнцестояния 2025 г.), время с шагом 30 мин. Зависимые: Δh, Δaz |
| Данные | Только расчёт; эталон — astropy (`AltAz` без рефракции, pressure = 0) |
| Процедура | Для каждой точки сетки считаем (h, az) нашим кодом до поправки на рефракцию и astropy; оставляем точки с h > 1°; поправку на рефракцию проверяем отдельно по формуле NOAA на 5 высотах |
| Метрики | max\|Δh\|, max\|Δaz\| (при h > 1°); доля совпадений признака «Солнце над горизонтом» |
| Интерпретация | ≤ 0,1° — ошибка окон низкого Солнца порядка минут, пренебрежимо мала для месячных окон. Больше — ищем ошибку в долготе, часовом поясе, рефракции |
| Провал | max\|Δh\| > 0,1° → модуль освещения не используется (атрибут light — «not assessed») до исправления |
| Воспроизведение | `pytest pipeline/common/tests/test_sun.py -k reference` |

| | |
| --- | --- |
| Вопрос | Считает ли `terrain_attributes` то, что заявлено, и совпадает ли с расчётом в Earth Engine? |
| Гипотезы | (a) Плоскость с уклоном 10° → p50 = 10 ± 0,1° на любой базе; горизонталь → 0; (b) расхождение GEE и Python по `slope_f400_p50` ≤ 0,5° или ≤ 10 % на каждом из 3 квадратов |
| Переменные | (a) поверхность (плоскость, конус, синусоида, шум), база (100 м, 400 м, 2 км); (b) квадрат (3 шт. из разных страт), реализация (GEE / Python) |

| Процедура | (a) pytest на аналитических поверхностях; (b) для 3 квадратов — расчёт `terrain_attributes` по скачанному DEM и сравнение с результатами ступени A |
| Метрики | Абсолютная и относительная ошибка по каждому атрибуту |
| Интерпретация | (a) верность формул; (b) систематическое расхождение означает разные определения (проекция, размер пикселя, база), случайное — разные данные |
| Провал | (a) — ошибка кода, задача не DONE; (b) — найти причину; если не нашли до 16:30 — атрибуты GEE помечаются «unverified» в ограничениях |
| Воспроизведение | `pytest pipeline/common/tests/test_terrain.py`; `python -m pipeline.earth.crosscheck --n 3` |

## E3. Восстановление практики по задачам (P0; VAL-01)

| | |
| --- | --- |
| Вопрос | Ставит ли соответствие задаче F_o высоко площадки, которые NASA и агентства документированно использовали **именно для этой задачи**? |
| Гипотеза H3 | Для задач, где причина выбора площадки выражается нашими атрибутами (рельеф, холод и сухость, освещение), медиана `pct` (ранг в % допущенных кандидатов) ≤ 20 % и лучше обеих базовых линий («только сухость», случайная) |
| Переменные | Независимая — способ ранжирования (F_o, три базовые линии). Зависимая — `pct` каждой пары. Группы — задачи (O1…O5, M1…M4) |
| Данные | `practice_sites.csv` (пары «площадка × задача», источники), `earth_candidates.json` (в т. ч. квадраты `PR_`), `targets.json`, `mission_templates.json`, `results.json` |
| Процедура | (1) До запуска: правила исключения применены, файл закоммичен. (2) Для каждой проверяемой пары берём квадрат `PR_` площадки и считаем его ранг среди допущенных кандидатов по F_o задачи против цели того же тела (основной анализ) и по F_o только из атрибутов без цели — пороги NASA, `at_least`, `at_most`, `colder` (дополнительный анализ, тоже пререгистрирован). (3) Те же ранги по базовым линиям. (4) Медианы по группам, hit@10 %, биномиальный тест против p0 = 0,10, кластерный бутстрэп по площадкам (одна площадка может быть в нескольких парах) |
| Базовые линии | (1) «только сухость»: `at_most(precip)·at_least(bare)`; (2) случайный порядок (ожидание 50 %); (3) общий балл v1 |
| Правила исключения (до запуска) | Причина выбора — химия, биология, пещеры, масштаб < 100 м, или источник не связывает площадку с задачей |
| Метрики | pct каждой пары; медиана по группам; hit@10 %; p-value биномиального теста; 95 % бутстрэп-интервал медианы |
| Интерпретация | Хорошо — атрибуты отражают причины, по которым эксперты выбирали площадки. Плохо — причины лежат вне наших данных (геология, логистика, традиция) или площадки выбирались не под нашу цель (например, тренировки Apollo — не под Mons Mouton): поэтому есть дополнительный анализ без цели |
| Провал | Медиана > 20 % или не лучше «только сухость» → `not_confirmed`; на сайте и в подаче «проверка не подтвердила»; утверждение C3 снимается. Проверяемых пар < 8 → `inconclusive` |
| Воспроизведение | `python -m pipeline.engine.validate_practice` |

## E4. Точность оптимизатора кампании (P0; ENG-02)

| | |
| --- | --- |
| Вопрос | Находит ли перебор на коротком списке оптимум, и насколько хуже жадный поиск? |
| Гипотезы | (a) На 100 случайных задачах с n ≤ 25 перебор совпадает с полным перебором всех наборов (100 %); (b) жадный ≥ (1 − 1/e) от оптимума (это теорема — фиксируем средний и худший разрыв, а не «подтверждаем») |
| Переменные | n (10…25), число задач m (3…6), k (1…3), матрица F ~ U(0, 1) с seed |
| Данные | Синтетические задачи; на реальных данных — поля `method.exact_coverage` и `method.greedy_coverage` в `results.json` |
| Процедура | Сгенерировать 100 задач; `exact_best` с U = все кандидаты против `itertools.combinations`; `greedy` против оптимума; на реальных данных — сравнить точный результат на коротком списке с жадным по всему пулу и отметить объединение |
| Метрики | Доля совпадений; средний и худший разрыв жадного; время для \|U\| = 120, k = 3 |
| Интерпретация | 100 % совпадений — код верен. Если на реальных данных жадный по всему пулу лучше точного на коротком списке — короткий список неполон; это видно в `merged_greedy` |
| Провал | (a) < 100 % → ошибка кода, оптимизатор не используется до исправления |
| Воспроизведение | `pytest pipeline/engine/tests/test_campaign.py -k exact` |

## E5. Устойчивость кампании и чувствительность к пропускам (P1; VAL-03)

| | |
| --- | --- |
| Вопрос | Меняется ли рекомендованная кампания от весов, допусков, состава пула и пропусков в данных? |
| Гипотеза | Площадка-лидер для каждой задачи выбирается в ≥ 60 % из 200 возмущённых запусков |
| Переменные | Веса × U(0,8; 1,2); допуски × U(0,7; 1,3); бутстрэп 80 % пула; маскирование 10 % значений атрибутов; seed 2026 |
| Данные | Входы `results.json` (те же файлы и хэши) |
| Процедура | 200 запусков `design()` с возмущениями; частоты выбора площадок и ролей; отдельно — 50 запусков только с маскированием (чувствительность к пропускам) |
| Метрики | Частота выбора площадок; медиана Жаккара с базовой кампанией; доля запусков с тем же покрытием ± 0,05 |
| Интерпретация | Высокая устойчивость — кампанию можно рекомендовать. Низкая — интерфейс показывает «несколько равноценных вариантов», а не одну кампанию; это находка, а не провал кода |
| Провал | < 60 % → `not_confirmed`, утверждение C10 не используется |
| Воспроизведение | `python -m pipeline.engine.robustness --runs 200 --seed 2026` |

## E7. Отрицательные контроли (P0; VAL-02)

| | |
| --- | --- |
| Вопрос | Не выигрывают ли заведомо неподходящие места, и не ломаются ли ограничения? |
| Гипотезы | (a) Ни один контрольный квадрат `CT_` (лес, пашня, ледник) не входит в топ-5 % ни одной задачи; (b) квадраты с водой > 0,5 или застройкой > 0,2 не допускаются (F = null, причина «constraint») |
| Переменные | Класс контроля (лес: доля деревьев > 0,7; пашня > 0,7; постоянный снег и лёд > 0,7) по 20 квадратов; задача |
| Данные | `earth_candidates.json`: 60 квадратов `CT_` с `pool = "control"` (добавляет EARTH-01; в кампаниях не участвуют), доли классов WorldCover в `context`; `results.json` |
| Процедура | Посчитать F_o контролей так же, как кандидатов; ранжировать среди допущенных кандидатов; проверить ограничения на синтетических значениях в тестах. Дополнительно — **проверка здравого смысла, не доказательство**: точная кампания ≥ жадной ≥ медианы 1 000 случайных (выполняется по построению) |
| Метрики | Доля контролей в топ-5 % по каждой задаче; число нарушений ограничений |
| Интерпретация | (a) выполнено — модель различает голую поверхность и растительность или лёд; не выполнено — атрибуты слишком грубые или ошибка в данных. Контроли «лёгкие»: они не доказывают, что модель различает похожие пустыни, — это делает только E3 |
| Провал | (a) нарушено → разбор каждого случая (SCI-05), исправление данных или признание ограничения; (b) нарушено → ошибка кода |
| Воспроизведение | `python -m pipeline.engine.controls --seed 2026` |
